# Архитектура

Этот документ описывает техническую архитектуру Termide.

## Общий обзор

Termide — это терминальная IDE, построенная на Rust с использованием TUI-фреймворка `ratatui`. Она использует адаптивную **компоновку с вертикально разделяемыми колонками панелей**: каждая панель в столбце имеет независимо регулируемую высоту, плюс однонажимный пресет полноэкранного режима для активной панели.

```
┌─────────────────────────────────────────────────────────┐
│ Строка меню  [CPU] [RAM] [Часы]                         │
├───────────────────┬─────────────────────────────────────┤
│ ┌[≡] 📁 Файлы ──┐ │ ┌[≡] 📝 Редактор: main.rs ────────┐│
│ │ src/          │ │ │                                  ││
│ │ tests/        │ │ │  fn main() {                     ││
│ │ Cargo.toml    │ │ │      // код здесь                ││
│ │               │ │ │  }                               ││
│ ├[≡] 💻 Терминал┤ │ │                                  ││
│ │ $ cargo build │ │ │                                  ││
│ │ Сборка...     │ │ │                                  ││
│ └───────────────┘ │ └──────────────────────────────────┘│
├───────────────────┴─────────────────────────────────────┤
│ Статус: file.rs:42  Стр 10, Кол 5       Диск: 83%      │
└─────────────────────────────────────────────────────────┘
```

В левой колонке выше — две панели с собственными высотами; справа — одна панель занимает всю колонку. Нажатие `Alt+F11` сворачивает все нефокусные панели в активной колонке до строки заголовка (пресет на одну строку), повторное нажатие восстанавливает прежние высоты.

## Основные архитектурные компоненты

### 1. Система компоновки

#### 1.1 LayoutManager

**Расположение:** `crates/layout/src/lib.rs`

`LayoutManager` владеет состоянием split-компоновки. Он управляет:

**Компоненты:**
- `panel_groups: Vec<PanelGroup>` - Горизонтальное расположение групп панелей
- `focus: usize` - Текущий фокус (индекс активной группы панелей)

**Ключевые обязанности:**
- Добавление панелей с автоматическим стекированием на основе порога ширины
- Управление горизонтальной навигацией (Alt+Left/Right)
- Управление вертикальным фокусом внутри группы (Alt+Up/Down)
- Умное стекирование/разделение панелей между группами (Alt+Backspace, F11)
- Пропорциональное перераспределение ширин при ресайзе терминала
- Закрытие панелей и очистка пустых групп

**Управление фокусом:**
Фокус — это простой индекс `usize`, указывающий, какая группа панелей в данный момент активна. Фокусная группа получает ввод с клавиатуры/мыши и подсвечивается в UI.

#### 1.2 PanelGroup

**Расположение:** `crates/layout/src/panel_group.rs`

`PanelGroup` представляет вертикальный split-стек панелей в одной колонке.

**Структура:**
```rust
pub struct PanelGroup {
    panels: Vec<Box<dyn Panel>>,         // Панели в этой группе
    expanded_index: usize,               // Фокусная панель (активная рамка)
    pub width: Option<u16>,              // Ширина колонки (None = авто-распределение)
    split_heights: Option<Vec<u16>>,     // Кешированные высоты панелей
    fullscreen_cache: Option<Vec<u16>>,  // Высоты до входа в fullscreen-пресет
}
```

**Поведение компоновки:**
- Все панели в группе видны. Минимальная высота каждой — одна строка (заголовок).
- `split_heights` — кеш per-panel высот. `None` означает «нет кеша — равномерное распределение при первом обращении». Высоты пропорционально пересчитываются при ресайзе.
- `Alt+F11` (action `toggle_fullscreen_panel`) переключает fullscreen-пресет: фокусная панель занимает всю высоту колонки, остальные сжимаются до одной строки. Высоты до пресета сохраняются в `fullscreen_cache` для restore при повторном нажатии.
- В пресете переключение фокуса через `Alt+Up`/`Alt+Down` (`prev_panel`/`next_panel`) переприменяет пресет к новому фокусу — визуально как старый аккордеон.
- `Alt+Shift+=` / `Alt+Shift+-` (`panel_grow_vertical` / `panel_shrink_vertical`) увеличивают/уменьшают фокусную панель на 1 строку, забирая/отдавая место соседу (cascade).

**Ключевые операции:**
- `add_panel()` / `insert_panel()` / `remove_panel()` — добавление/удаление с ребалансировкой кешей высот.
- `set_expanded()` / `next_panel()` / `prev_panel()` — перемещают фокус; переприменяют пресет, если он активен.
- `toggle_fullscreen()` — включение/выключение пресета.
- `grow_focused()` / `shrink_focused()` — изменение высоты фокусной панели.
- `resize_panel_divider()` — применение дельты к разделителю над указанной панелью (используется обработчиком mouse drag).

#### 1.3 Автоматическое стекирование

При добавлении новой панели через `LayoutManager::add_panel()`:

```rust
let new_width_if_split = available_width / (num_groups + 1);

if new_width_if_split < config.auto_stack_threshold {
    // Стекировать вертикально в активную группу (split с кешем высот)
    active_group.add_panel(panel);
} else {
    // Создать новую горизонтальную группу
    let new_group = PanelGroup::new(panel);
    panel_groups.push(new_group);
}
```

**Порог по умолчанию:** `auto_stack_threshold = 80` символов

Это гарантирует, что панели всегда имеют достаточно места для использования.

### 2. Система панелей

#### 2.1 Трейт Panel

**Расположение:** `crates/core/src/lib.rs`

Все панели реализуют трейт `Panel`, который определяет интерфейс для интерактивных терминальных панелей:

```rust
pub trait Panel {
    /// Отрисовать содержимое панели
    fn render(
        &mut self,
        area: Rect,                // Доступная область рендеринга
        buf: &mut Buffer,          // Буфер ratatui
        is_focused: bool,          // Имеет ли эта панель фокус?
        panel_index: usize,        // Индекс панели для идентификации
        state: &AppState,          // Общее состояние приложения
    );

    /// Обработать ввод с клавиатуры
    fn handle_key(&mut self, key: KeyEvent) -> Result<()>;

    /// Обработать ввод мыши
    fn handle_mouse(&mut self, mouse: MouseEvent, panel_area: Rect) -> Result<()>;

    /// Получить заголовок панели (показывается в шапке)
    fn title(&self) -> String;

    /// Проверить, является ли это панелью приветствия (автоматически закрывается при открытии других)
    fn is_welcome_panel(&self) -> bool { false }

    /// Получить файл для открытия (для панелей, запрашивающих открытие файла)
    fn take_file_to_open(&mut self) -> Option<PathBuf> { None }

    /// Получить рабочую директорию для новых панелей
    fn get_working_directory(&self) -> Option<PathBuf> { None }

    /// Получить запрос модального окна (для панелей, открывающих модальные окна)
    fn take_modal_request(&mut self) -> Option<(PendingAction, ActiveModal)> { None }
}
```

### 3. Обработка событий

#### 3.1 Цикл событий

**Расположение:** `crates/app/src/app/mod.rs`

Структура основного цикла событий:

```rust
while !state.should_quit {
    match event_handler.next()? {
        Event::Key(key) => self.handle_key_event(key)?,
        Event::Mouse(mouse) => self.handle_mouse_event(mouse)?,
        Event::Resize(w, h) => state.update_terminal_size(w, h),
        Event::Tick => {
            // Периодические обновления
            self.update_panels_tick()?;
            self.system_monitor.update(&mut self.state);
        }
    }
    self.render(terminal)?;
}
```

**Типы событий:**
- **Key** - Ввод с клавиатуры (горячие клавиши, ввод текста)
- **Mouse** - Клики мыши, перетаскивание, прокрутка
- **Resize** - Изменение размера терминала
- **Tick** - Периодический таймер (мониторинг ресурсов, обновление панелей)

#### 3.2 Обработчик клавиш

**Расположение:** `crates/app/src/app/key_handler.rs`

Обрабатывает ввод с клавиатуры с приоритетом:

1. **Модальное окно захватывает ввод первым** (если открыто)
2. **Глобальные горячие клавиши** (Alt+M, Alt+H, Alt+Q и т.д.)
3. **Управление панелями** (Alt+Left/Right, Alt+Up/Down, Alt+X и т.д.)
4. **Активная панель** (через `panel.handle_key()`)

**Поддержка кириллицы:**
Трансляция раскладки клавиатуры через `termide_keyboard::KeyNormalizer::canonicalize()` позволяет горячим клавишам работать с русской раскладкой.

#### 3.3 Обработчик мыши

**Расположение:** `crates/app/src/app/mouse_handler.rs`

Обрабатывает ввод мыши:

**Заголовок панели:**
- Клик по кнопке `[≡]` → Открыть контекстное меню действий панели (Закрыть / Отделить / Объединить / Переместить)
- Клик по title → Активировать панель (двойной клик по файловому менеджеру → выбор каталога)
- **Drag за title** → Двухрежимный жест:
  - Drop внутри колонки исходной группы → вертикальный resize (делитель над панелью прыгает к курсору).
  - Drop в другой колонке или между колонками → перенос панели: толстая линия показывает, куда встанет панель; drop на заголовок другой панели вставляет в её группу, drop между группами создаёт новую. `Escape` отменяет.

**Содержимое панели:**
- Клики перенаправляются в `panel.handle_mouse()`
- Каждая панель обрабатывает свои собственные взаимодействия с мышью

**Строка меню:**
- Клик по пунктам меню для активации

#### 3.4 Обработчик модальных окон

**Расположение:** `crates/app/src/app/modal_handler.rs` и `crates/modal/src/`

Обрабатывает интерактивные модальные диалоги:

**Типы модальных окон** (крейт `termide-modal`):
- **Input** — ввод текста (имя файла, имя директории и т.д.)
- **Confirm** — подтверждение Да/Нет
- **Select** / **EditableSelect** — выбор из вариантов (с возможным редактированием)
- **Choice** — горизонтальные кнопки выбора
- **Info** — отображение информации с **прокручиваемым содержимым** (отчёты скриптов, системная информация); скроллбар на правой рамке, клавиши `↑↓/PageUp/PageDown/Home/End` и колесо мыши
- **InfoAction** — info-окно с дополнительными кнопками действий
- **Settings** — полноэкранный модал конфигурации с **sidebar-layout**. Разбит на подмодули в `crates/modal/src/settings/`:
  - `settings.rs` — структура `SettingsModal`, рендер, обработка клавиш/мыши
  - `settings/fields.rs` — декларативные данные полей (`FieldType`, `FieldDescriptor`, `ContentRow`, функции `fields_for_tab`, `get_field_value`, `toggle_field`, `cycle_enum_*`)
  - `settings/kb.rs` — макросы и таблицы keybindings (`kb_get!`/`kb_set!`, `KB_SECTIONS`, `kb_binding_names`, `get/set_kb_value`, `format_key_event`)
- **Progress** — progress-bar для длительных операций
- **Commit** / **Conflict** / **RenamePattern** / **Projects** / **DirectoryPicker** / **SaveAs** / **BookmarkAdd** / **Calendar** / **CommandPalette** / **ScriptCreate** — специализированные диалоги для отдельных операций

Общие утилиты вынесены в `crates/modal/src/base.rs` (`render_modal_block`, `render_modal_frame`, `button_style`, `CursorNavigation` trait).

**Захват ввода:**
Когда модальное окно открыто, ввод с клавиатуры сначала идёт в модальное окно. Escape закрывает модальное окно.

### 4. Конвейер рендеринга

#### 4.1 Основной рендеринг

**Расположение:** `src/ui.rs` (`render_layout_with_accordion`)

Поток рендеринга:

```rust
fn render_main_area(frame, layout_manager, state) {
    // 1. Вычислить ширины колонок (пропорциональные, с floor min_panel_width).
    let horizontal_chunks = calculate_horizontal_layout();

    // 2. Для каждой колонки взять вертикальные ограничения из кеша
    //    высот группы (или равномерное распределение по умолчанию).
    for group in groups {
        let vertical_chunks =
            termide_layout::compute_vertical_constraints(group, area_height);

        // 3. Отрисовать каждую панель. Панели с height >= 2 рисуются
        //    с полной рамкой (включая нижнюю) и контентом; панели
        //    сжатые до одной строки — только заголовок.
        let mut prev_was_accordion = false;
        for (idx, panel) in group.panels().enumerate() {
            let area = vertical_chunks[idx];
            let omit_bottom_border = area.height < 2;
            if !omit_bottom_border {
                render_expanded_panel(panel, area, omit_bottom_border, ...);
            } else {
                render_collapsed_panel(panel, area, ...);
            }
            // Углы верхней строки выбираются по контексту: └┘
            // для последней панели если она accordion (группа
            // визуально замыкается), ├┤ если обе соседние панели
            // accordion (непрерывность), иначе обычные ┌┐.
            patch_top_corners(area, idx, prev_was_accordion, &group);
            prev_was_accordion = area.height < 2;
        }
    }

    // 4. Отрисовать модальное окно (если открыто).
    if let Some(modal) = state.active_modal {
        render_modal(modal, ...);
    }
}
```

Каждая панель с `height >= 2` рисует **полную** рамку; между двумя соседними панелями видны две соседние строки рамок (низ верхней + верх нижней) — это делает фокусную панель полностью обведённой акцентным цветом со всех четырёх сторон. Accordion-сжатые `height == 1` панели сохраняют top-only border, их верхние углы переключаются между `┌┐`, `├┤` и `└┘` в зависимости от того, что находится над ними и являются ли они последними в группе.

#### 4.2 Рендеринг панелей

**Расположение:** `crates/ui-render/src/panel_rendering.rs`

**Полная панель (height ≥ 2 строк):**
- Граница с кнопкой действий `[≡]` и emoji + заголовком (напр. `[≡] 📁 Файлы`)
- Полная область содержимого
- Прокручиваемо, если содержимое превышает область
- Нижний бордер всегда рисуется для панелей с `height >= 2`; между двумя соседними панелями видны две строки рамок подряд, что позволяет полностью обвести фокусную панель акцентным цветом со всех четырёх сторон

**Сжатая панель (height = 1 строка, только когда сжата до минимума):**
- Только заголовок: `─[≡] 📁 Файлы ─────`
- Занимает одну строку
- Клик по заголовку фокусирует панель; `Alt+F11` или `Alt+Shift+=` увеличивает её

**Режим иконок:**
Заголовки панелей показывают emoji-иконки по типу панели (📁 файловый менеджер, 💻 терминал, 📝 редактор, 🔄 операции, 🚧 диагностика, 📑 outline, 🎨 image и т.д.). Все иконки выбраны так, чтобы надёжно занимать 2 клетки в современных терминалах — это сохраняет выравнивание заголовка после иконки. Режим настраивается через `icon_mode` в секции `[general]`:
- `auto` (по умолчанию) — emoji, если терминал поддерживает, иначе просто `[≡]`
- `emoji` — всегда показывать emoji-иконки
- `unicode` — без иконок, без стрелок, только `[≡]`

**Drag Overlay:**
При перетаскивании панели за верхний бордюр `render_drag_overlay()` (в `src/ui.rs`) вызывается после основного рендера панелей и до dropdown/modal. Что рисовать, задаёт намерение (`PanelDragIntent::ResizeAbove`, `PanelDragIntent::Move { target: IntoGroup, drop_y }` или `PanelDragIntent::Move { target: NewGroup, .. }`): толстую линию `━` на строке `drop_y` для `ResizeAbove` и `IntoGroup` (будущий разделитель / строка разбиения) или толстую линию `┃` в колонке промежутка для `NewGroup`. Ghost-иконки нет — операцию читают по форме и положению линии. Хит-тест переиспользует `calculate_panel_rects` / `classify_panel_drag` / `compute_drop_target` из `termide_layout`, так что mouse-обработчик и рендер согласованы по геометрии. Отдельный оверлей `render_v_divider_ghost` обслуживает перетаскивание за нижний бордюр внутри группы (`Vertical­Divider­Drag­State`) и рисует линию `━` во всю ширину затронутой группы.

**Рендеринг границ:**
Границы и кнопки рисуются с помощью `panel_rendering.rs`, затем метод `render()` панели рисует содержимое во внутренней области.

### 8. Раскладки проектов

**Расположение:** `crates/project/src/lib.rs`

Раскладка панелей каждого проекта сохраняется и восстанавливается (`ProjectLayout`):

**Расположение хранилища:** всё, что termide хранит о проекте, кроме сессий
агента, лежит в одном плоском каталоге на проект
(`crates/project/src/store.rs`):

- Linux: `~/.local/share/termide/projects/<имя>-<хеш>/`
- macOS: `~/Library/Application Support/termide/projects/<имя>-<хеш>/`

`<имя>` — имя каталога корня, сведённое к `[A-Za-z0-9_-]`, `<хеш>` — 12
шестнадцатеричных цифр от канонического пути корня, так что ни один символ
пути не нужно экранировать. Сам корень читается из `project.toml`, а не из
имени.

```
projects/<имя>-<хеш>/
├── project.toml   # root = "/путь"; [layout]
├── trust.toml     # [ai.permissions] правила «разрешить всегда»; [approved]
├── owner.lock     # держит экземпляр, в котором проект открыт
├── owner.toml     # какой это экземпляр
├── logs/          # <дата>-<время>.log, по одному на запуск, хранятся 24 часа
└── buffers/       # <дата>-<время>.txt, несохранённое содержимое редакторов
```

Сессии агента остаются в `ai/sessions/<путь проекта>/`, рядом с агентами.
Проект живёт, пока его держит пользователь: удаление из меню «Проекты» или
переключателя (`F8`) убирает его каталог, а по желанию пользователя — и сессии
агента. По возрасту удаляются только логи; каталог, в котором ничего не
осталось, убирается при запуске.

Удаление и перенос сначала захватывают `owner.lock` проекта, так что проект,
открытый в другом экземпляре, никогда не уходит у него из-под ног, а файл
блокировки удаляется последним, ещё удерживаемым.

Каталог данных прежнего устройства — `sessions/` или `projects/` в виде
дерева, повторяющего пути проектов, с файлами `session.toml`, `session-*.log`
и `unsaved-*`, а также деревья `trust/` и `locks/` — при первом запуске
сливается в новое; каждый перенос и каждая ошибка записываются в панель
**Журнал**. Старая версия termide, запущенная рядом с новой, не видит её
блокировок.

**Возможности:**
- Автоматическое сохранение раскладки при выходе
- Восстановление раскладки панелей при запуске
- Переключение между проектами через меню «Проекты»
- Проекты, корня которых больше нет, отмечены в меню знаком ✗

`project.toml` заменяется атомарно (запись во временный файл, сброс на диск,
переименование), как и несохранённые буферы, так что сбой никогда не
оставляет полфайла. `project.toml`, который не удаётся разобрать —
повреждённый или записанный более новой версией termide, — переименовывается
в `project.toml.broken-<время>`, и это отмечается в **Журнале**; проект
открывается в раскладке по умолчанию, несохранённые буферы восстанавливаются
как панели редактора, а следующее сохранение пишет новый файл, не уничтожая
старый.

**Формат файла раскладки:**
```toml
root = "/home/user/project"

[layout]
focused_group = 0

[[layout.panel_groups]]
expanded_index = 1            # фокусная панель в группе
width = 80                    # ширина колонки (None = авто-распределение)
split_heights = [12, 6]       # per-panel высоты (отсутствуют, если кеша нет)
fullscreen_cache = [10, 8]    # высоты для restore при выключении Alt+F11

[[layout.panel_groups.panels]]
type = "file_manager"
path_or_url = "/home/user/project"

[[layout.panel_groups.panels]]
type = "editor"
path = "/home/user/project/main.rs"
```

Поле `mode = "accordion"` из старых раскладок проектов по-прежнему читается и инициирует одноразовую миграцию в fullscreen-пресет (текущий код его не пишет).

### 9. VFS (удалённые файловые системы)

**Расположение:** `crates/vfs/src/`

Чисто-Rust слой VFS делает удалённые серверы похожими на локальные каталоги для
остального приложения. Без нативного OpenSSL или libssh — SFTP работает на
`russh` + `russh-sftp`, FTPS на `rustls`, SMB на `smb2`, NFSv3 на
`nfs3_client`. Сборки статически работают на
Alpine / musl.

**Поддерживаемые протоколы:** `sftp://`, `ftp://`, `ftps://`, `smb://`,
`nfs://`.

**Ключевые компоненты:**
- **Трейт `VfsProvider`** (`crates/vfs/src/traits.rs`) — абстрактный API
  файловой системы, используемый FileManager, file-ops и редактором: `list_dir`,
  `read_file`, `write_file`, `delete`, `upload`, `upload_with_progress` и т.д.
  Каждый вызов возвращает `VfsOperation<T>`, чей receiver опрашивает вызывающий —
  блокирующего варианта нет.
- **`VfsManager`** (`crates/vfs/src/lib.rs`) — кэш провайдеров по ключу
  `(scheme, host, port, user)`; вытесняет записи, чей актор умер.
- **SFTP-актор** (`crates/vfs/src/sftp/`) — единственная tokio-задача владеет
  сессией `russh-sftp` и обрабатывает малые атомарные команды (`OpenRead` /
  `ReadChunk` / `WriteChunk` / `CloseHandle` / `Stat` / `ListDir` /
  `MkdirRecursive` / …). Циклы чанков живут на стороне синхронного воркера,
  опрашивая паузу/отмену между отправками.
- **SMB и NFS** (`crates/vfs/src/smb.rs`, `nfs.rs`) — асинхронные клиенты на
  одном общем tokio-рантайме (`rt.rs`). Их загрузки и скачивания — файла или
  целого дерева — идут в `chunked.rs` в отдельном потоке, по куску на
  блокирующий вызов, с прогрессом, паузой и отменой между кусками.
- **Разбор URL** (`crates/vfs/src/url.rs`) — round-trip UTF-8 с
  percent-декодированием путей, чтобы не-ASCII имена файлов сохранялись.
- **Аутентификация** — SSH-агент → `IdentityFile` из `~/.ssh/config` → ключи по
  умолчанию (`id_ed25519` / `id_rsa` / `id_ecdsa` / `id_dsa`) → пароль, причём все
  четыре доступны как явные варианты `AuthMethod` для тех, кто не хочет
  авто-цепочку.

**Безопасность отмены:** передачи отменяются между чанками; для частичных файлов
показывается модал «Удалить частичную загрузку?», чтобы сервер не хранил
осиротевшие байты. Переименования в рамках одного соединения остаются на стороне
сервера (без download-then-upload). Пользовательский взгляд — в
`doc/ru/vfs.md`, поток отмены — в `doc/ru/operations.md`.

### 10. Хранилище паролей

**Расположение:** `crates/secrets/` (хранение), `crates/app/src/app/vault.rs`
(запросы и маршрутизация), `crates/core/src/credentials.rs` (контракт).

`termide-secrets` — хранилище без UI: один TOML-файл, секреты в котором
запечатаны на открытый ключ X25519, а закрытый ключ зашифрован мастер-ключом,
полученным через Argon2id. Для записи нужен только открытый ключ, для чтения —
разблокированный закрытый. Запись идёт по схеме «прочитать — изменить —
записать» под файлом блокировки, затем атомарный rename.

Панели хранилища не видят. Панель, которой отказали во входе, отправляет
`PanelEvent::CredentialsRequired { url, attempt }` с URL без пароля.
Приложение отвечает одним из двух способов:

- из хранилища, спросив мастер-пароль, если оно заблокировано;
- спросив пароль у пользователя.

Затем оно рассылает `PanelCommand::ProvideCredentials` (или
`CancelCredentials`), и команду берёт панель, ждущая этот URL. При успехе
панель отправляет `CredentialsAccepted`, и только тогда записывается пароль,
который пользователь попросил сохранить. Сетевые операции git идут тем же
путём со стороны приложения: отказ распознаётся по stderr git, повтор идёт
через askpass-помощник. Отложенное действие любого запроса хранилища —
пустой `PendingAction::Vault`; то, для чего запрос, включая секреты, остаётся
в `VaultState` приложения. Взгляд пользователя — в `doc/ru/passwords.md`.

## Архитектурные решения

### Почему split-компоновка с fullscreen-пресетом?

**Проблема:** Пространство терминала ограничено, многопанельные IDE часто кажутся тесными — но и бинарная схема «одна развёрнутая, остальные свёрнуты» тоже отбрасывает случаи, когда пользователю нужно одновременно видеть две-три панели в подобранных пропорциях.

**Решение:** Регулируемый split per-group плюс однонажимный fullscreen-пресет:
- Все панели в группе видны по умолчанию; пользователь подбирает высоты мышью (drag за нижний бордюр панели или drag за заголовок внутри колонки) либо `Alt+Shift+=` / `Alt+Shift+-`.
- `Alt+F11` переключает «полноэкранный пресет» для активной панели — фокусная панель занимает всю колонку, остальные сжимаются до строки заголовка; высоты до пресета сохраняются для мгновенного restore.
- Высоты кешируются и пропорционально пересчитываются при ресайзе терминала.
- Автоматическое стекирование между группами по-прежнему срабатывает на узких терминалах (`auto_stack_threshold`).

### Почему динамические панели?

**Преимущество:** Пользователи могут открывать столько панелей, сколько нужно:
- Несколько редакторов для разных файлов
- Несколько терминалов для разных задач
- Несколько файловых менеджеров для разных директорий

**Вызов:** Эффективное управление множеством панелей
- Fullscreen-пресет даёт чистый вид «одна панель на весь экран» по требованию
- Горячие клавиши обеспечивают быструю навигацию
- Экран приветствия автоматически закрывается

### Почему панели на основе трейтов?

**Гибкость:** Новые типы панелей можно добавлять без изменения основного кода
- Реализовать трейт `Panel`
- Добавить в логику создания панелей
- Работает с существующей системой компоновки

**Полиморфизм:** `Box<dyn Panel>` позволяет гетерогенные коллекции
- Единственный `Vec<Box<dyn Panel>>` содержит все типы панелей
- Единообразный рендеринг и обработка событий
- Накладные расходы динамической диспетчеризации незначительны для TUI

## Характеристики производительности

**Рендеринг:** O(n), где n = количество панелей в видимых группах
- Панели с height ≥ 2 рендерят полное содержимое; панели сжатые до 1 строки рендерят только заголовок
- Каждая панель с `height >= 2` рисует собственный нижний бордюр; соседние панели показывают две строки рамок подряд — фокусная панель полностью обведена акцентным цветом со всех сторон

**Обработка событий:** O(1) для большинства операций
- Прямой доступ по индексу к панели с фокусом
- Поиск в хеш-таблице для привязок клавиш

**Память:** Линейно от количества панелей
- Каждая панель владеет своим состоянием
- Общий AppState небольшой
- Нет избыточного клонирования (используются ссылки)

**Файловые операции:** Асинхронно, где возможно
- Наблюдатель файловой системы использует отдельный поток
- Дебаунсинг предотвращает избыточные обновления

### Асинхронные конвейеры

Несколько операций старта и горячего пути, которые раньше блокировали цикл
рендеринга, теперь выполняются на рабочих потоках и опрашиваются из `tick()`
каждой панели. Схема везде одна и та же: запустить воркер, «припарковать»
`mpsc::Receiver` на панели, подставить результат, когда `try_recv()` вернёт
данные. Ссылки ниже указывают, где живёт каждый конвейер.

| Конвейер                                   | Расположение воркера                                            | Опрашивается в                                                                        |
|--------------------------------------------|-----------------------------------------------------------------|---------------------------------------------------------------------------------------|
| Первичное чтение каталога FileManager      | `crates/panel-file-manager/src/lib.rs` (`start_async_reload`)   | `check_async_reload` из `check_background_panel_updates` (per-tick приложения)         |
| Разворачивание поддерева FileManager        | `crates/panel-file-manager/src/lib.rs` (`start_listing`)        | `poll_pending_expansions` оттуда же; строки-заглушки показывают `…` до готовности      |
| Git-статус по записям FileManager           | `crates/panel-file-manager/src/git_status.rs`                   | `check_git_status_async`; `apply_git_statuses` переприменяет, если чтение опередило    |
| Обновление панелей Git status / log         | `crates/panel-git-status/src/lib.rs`, `panel-git-log/src/lib.rs`| `poll_refresh` в `tick` каждой панели                                                  |
| Поиск репозиториев (RepoManager)         | `crates/git/src/repo_manager.rs` (`spawn_repo_walk`)            | `RepoManager::poll` из `tick` git-панели; вложенные репозитории и сабмодули на глубину 3, клоны, которые репозиторий игнорирует или не отслеживает, — из одного `git ls-files --others --directory`, репозиторий, содержащий проект, убирается когда обход завершится |
| Восстановление раскладки — панели параллельно | `crates/app/src/layout_store.rs` (`construct_panel` на панель)| Джойнятся синхронно после запуска, так что самая медленная панель гейтит первый кадр   |
| Регистрация репозиториев вотчером           | `crates/watcher/src/lib.rs` (`watch_repository`)                | `poll_pending` в главном цикле; inotify ставится чанками по `INSTALL_CHUNK` за тик, FSEvents (macOS) — один рекурсивный вотч на корень с фильтрацией по `.gitignore` при доставке |

Бэкенд SFTP/FTP использует другую схему — выделенный tokio-рантайм владеет
соединением и актором «чанк-как-команда» (см. `crates/vfs/src/sftp/`).
Синхронный воркер крутит цикл чанков и между отправками опрашивает флаги
паузы/отмены, поэтому приостановленная передача оставляет актор свободным для
обслуживания запросов метаданных от других панелей.

## Будущие архитектурные соображения

**Потенциальные улучшения:**

1. **Асинхронные панели**
   - Долго выполняющиеся операции (поиск, компиляция) не блокируют UI
   - Фоновые задачи с индикаторами прогресса

2. **Панели плагинов**
   - Плагины (`crates/plugins`, см. `doc/en/plugins-design.md`) работают как
     процессы рядом с termide; их собственные панели, нарисованные по
     присланной модели rich-text, — следующий этап

3. **Сетевые панели**
   - SSH терминальные панели
   - Удалённые браузеры файлов
   - Совместное редактирование

## Отладка архитектуры

**Система логирования:**
- Каждый запуск пишет свой лог в каталог `logs/` проекта или в `[logging] file_path` (см. руководство разработчика)
- Уровни: trace, debug, info, warn, error
- Метки времени и префиксы компонентов
- Логи старше 24 часов удаляются при запуске

**Панель отладки:**
- Живой просмотр состояния приложения
- Недавние записи логов
- Инспекция панелей
- Метрики производительности

**Обработка паник:**
- Восстановление терминала при панике
- Запись информации о панике в лог
- Показ сообщения об ошибке пользователю

## Соображения безопасности

**Инъекция в терминал:**
- ANSI escape-последовательности фильтруются в терминальной панели
- Пользовательский ввод санитизируется перед выполнением в оболочке

**Файловые операции:**
- Атаки через симлинки предотвращаются
- Проверки path traversal
- Проверка прав доступа перед операциями

**Лимиты ресурсов:**
- Лимит размера файла (100 МБ) для редактора
- Лимит буфера прокрутки для терминала
- Файл журнала больше 10 МБ откладывается как `<имя>.1` и начинается заново

**Недоверенные проекты:**
Файлы проекта приходят с репозиторием, поэтому ничто в них не решает, что
запускает termide, куда уходит ключ и насколько свободно действует агент.
- `.termide/config.toml` проходит через `config::layer_rules`: из него
  отбрасываются программы (отладчики, LSP-серверы, шелл, браузер), файл
  журнала, адрес подключения и переменная с ключом, режим агента и правила
  `allow`, предел сообщений между агентами и время блокировки хранилища; окно настроек показывает эти поля как только глобальные
- Плагины лежат только в глобальном каталоге плагинов; проект переключает
  плагин в пределах режима, заданного глобальным конфигом
- MCP-серверы, хуки и команды `commands.toml` проекта запускаются только после
  одобрения в нынешнем виде (`agent_core::approvals`), а его агенты стартуют
  только в `plan` или `ask` и никогда не бывают внешними
- Решения пользователя о проекте — одобрения, правила «allow always» —
  хранятся в `trust.toml` проекта в каталоге данных termide, а не в проекте

## Заключение

Архитектура Termide приоритизирует:
- **Гибкость** - Динамическая система панелей адаптируется к потребностям пользователя
- **Эффективность** - Регулируемая split-компоновка с однонажимным fullscreen-пресетом максимизирует используемое пространство, не отказываясь от многопанельных видов
- **Расширяемость** - Дизайн на основе трейтов позволяет лёгкие дополнения
- **Надёжность** - Оборонительное программирование предотвращает сбои
- **Производительность** - Эффективный рендеринг и обработка событий

Split-компоновка с fullscreen-пресетом — ключевая инновация, которая отличает Termide от традиционных многопанельных терминальных приложений.
