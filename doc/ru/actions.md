# Пользовательские команды

> **Примечание:** этот документ описывает **пользовательские команды** в меню `Команды`. Клавиатурные сочетания и действия интерфейса — в [ui.md](ui.md#клавиатурная-навигация-и-управление-по-меню-и-панелям).

Команда — это именованная строка оболочки, которую Termide запускает из меню `Команды` или по собственной горячей клавише: в новой панели терминала, незаметно в фоне или в фоне с показом вывода в окне по завершении. Команды описываются в файлах `commands.toml` — вручную или через форму `Добавить команду...`.

## Где хранятся команды

Файлов два, и меню показывает оба:

| Область | Файл |
|---------|------|
| Глобальные (для всех проектов) | `commands.toml` в каталоге конфигурации Termide |
| Проект | `<проект>/.termide/commands.toml` |

Каталог конфигурации зависит от платформы:

| Платформа | Глобальный файл |
|-----------|-----------------|
| Linux | `~/.config/termide/commands.toml` (или `$XDG_CONFIG_HOME/termide/commands.toml`) |
| macOS | `~/Library/Application Support/termide/commands.toml` |
| Windows | `%APPDATA%\termide\commands.toml` |

Файл проекта относится к текущему корню проекта, поэтому его можно закоммитить и разделить со всеми, кто работает с репозиторием.

Файлы не переопределяют друг друга: команда проекта и глобальная команда с одинаковым идентификатором — два отдельных пункта меню. Команды проекта идут первыми и выделены жирным.

Файл проекта приходит с репозиторием, поэтому команда проекта запускается, только когда вы её увидели. При первом запуске — из меню, палитры, по её горячей клавише или `F5` — окно показывает, что она запускает (сначала `build`, затем саму команду), и спрашивает; согласие запускает её и одобряет в нынешнем виде, в каталоге данных termide под именем проекта (`trust/<путь проекта>/approved.toml`). Если репозиторий изменит команду, её режим, `build`, отладчик или клавишу, вопрос повторится. Пока команда проекта не одобрена, её горячая клавиша спрашивает, только если это сочетание с `Ctrl` или `Alt` или F-клавиша: нажатие показывает то же окно, что и меню. Клавиша, которой набирают текст, — обычная буква, `Shift`+буква, `Enter` — привязывается, только когда команда одобрена: запустите её один раз из меню, и клавиша начнёт действовать. Команда, которую вы пишете в форме `Добавить команду...` или **Set up debugging**, одобряется при сохранении.

## Формат файла

Каждая таблица TOML — одна команда; имя таблицы — идентификатор команды.

```toml
[build]
command = "cargo build --release"

[test]
name = "Run tests"
command = "cargo nextest run"
group = "cargo"
key = "Ctrl+Shift+T"

[clippy]
command = "cargo clippy --workspace -- -D warnings"
mode = "report"
group = "cargo"

[dev-server]
name = "Start dev server"
command = "npm run dev > /tmp/dev-server.log 2>&1"
mode = "background"
```

| Поле | Обязательное | Описание |
|------|--------------|----------|
| `command` | да | Строка оболочки для запуска |
| `name` | нет | Название в меню; если его нет, показывается идентификатор |
| `mode` | нет | `terminal` (по умолчанию), `background` или `report`, см. [Режимы запуска](#режимы-запуска) |
| `cwd` | нет | `panel` (по умолчанию) — в рабочем каталоге панели в фокусе; `project` — в корне проекта |
| `group` | нет | Помещает команду в подменю с этим именем |
| `key` | нет | Горячая клавиша, запускающая команду, например `Ctrl+Shift+D`, см. [Горячие клавиши](#горячие-клавиши) |
| `params` | нет | Значения, которые запрашиваются перед запуском, см. [Параметры](#параметры) |
| `debugger` | нет | `lldb-dap`, `gdb-dap`, `debugpy`, `dlv-dap`, `lldb`, `gdb`, `dlv` или `pdb`: команда запускается под этим отладчиком, см. [Отладка](#отладка) |
| `build` | нет | Вместе с `debugger`: команда оболочки, которая выполняется первой; отладчик запускается, только если она прошла успешно |
| `console` | нет | С отладочным адаптером: `terminal` (по умолчанию) запускает программу в панели терминала, где она читает клавиатуру; `panel` показывает её вывод в панели отладки |

Неизвестное значение `mode` означает `terminal`. Если файл не разбирается, ни одна из его команд не появится; причина пишется в лог.

## Меню «Команды»

Меню `Команды` в строке меню содержит сверху вниз:

1. `Добавить команду...` — открывает форму новой команды.
2. Команды проекта без группы, затем группы проекта (жирным).
3. Глобальные команды без группы, затем глобальные группы.

Внутри каждой части команды и группы отсортированы по идентификатору и имени группы. Группа открывает подменю со своими командами; повторный клик по заголовку группы закрывает его. Горячая клавиша команды показывается в колонке сочетаний. Если терминал поддерживает эмодзи, перед названием стоит значок режима: 💻 терминал, ⚙ фон, 📋 отчёт, 🐞 команда с `debugger`.

Клавиши на выбранной команде:

| Клавиша | Действие |
|---------|----------|
| `Enter` | Запустить команду |
| `F2` | Переименовать (изменить идентификатор) |
| `F4` | Редактировать в форме команды |
| `Delete` / `F8` | Удалить после подтверждения |

Меню перечитывает оба файла при каждом открытии, поэтому команды, добавленные в файл вручную, появляются без перезапуска.

## Добавление и редактирование команд

`Добавить команду...` и `F4` открывают одну и ту же форму:

| Поле | Назначение |
|------|------------|
| `Группа:` | Имя группы; предлагает существующие группы. Пустое — верхний уровень меню |
| `Пункт меню:` | Название в меню (`name`) |
| `Команда:` | Строка оболочки (`command`); обязательна при создании |
| `Режим:` | `Терминал`, `Фоновый` или `Отчёт`; переключается `←` / `→` или `1`–`3` |
| `Запускать из папки проекта` | `cwd`: отмечено — команда идёт в корне проекта, не отмечено — в рабочем каталоге панели в фокусе |
| `Хоткей:` | Необязательная горячая клавиша (`key`) |
| `Команда проекта` | Отмечено — команда сохраняется в `.termide/commands.toml` проекта; не отмечено — в глобальный файл |

Идентификатор новой команды берётся из `Пункт меню:`, а если он пуст — из `Команда:`; символы `/ \ : * ? " < > | .` заменяются на `-`. Если команда с таким идентификатором уже есть, новая получает свободный вариант (`build-2`) и не заменяет её. Если при редактировании очистить `Пункт меню:`, метка удаляется, и меню показывает идентификатор. Переключение `Команда проекта` при редактировании переносит команду в другой файл. Галочка `Запускать из папки проекта` — это `cwd`: отмеченная пишет `cwd = "project"`, снятая убирает ключ, и команда следует за панелью в фокусе. Форма не редактирует `params`: он остаётся таким, как в файле. Переименование (`F2`) в идентификатор другой команды отклоняется.

Сохранение из формы, переименование и удаление правят `commands.toml` на месте: остальные команды, их порядок и комментарии вокруг остаются как были, переписываются только изменившиеся поля, а новая команда добавляется в конец. Переименованная команда переезжает в конец файла.

## Режимы запуска

Команда с `debugger` при любом `mode` запускается в корне проекта, в панели отладки или в панели терминала, см. [Отладка](#отладка). Любая другая команда запускается в рабочем каталоге панели в фокусе (например, в каталоге, открытом в файловом менеджере, или в текущем каталоге терминала), а если у панели его нет — в корне проекта. С `cwd = "project"` команда запускается в корне проекта при любой панели в фокусе: это неподвижная точка, от которой пишутся её относительные пути, та папка, в которой лежит её собственный `commands.toml`. Где команда запускается, входит в то, что покрывает одобрение: изменив `cwd`, проектную команду нужно одобрить заново.

| Режим | Как запускается | Вывод |
|-------|-----------------|-------|
| `terminal` | Открывается новая панель терминала, и строка команды вводится в её оболочку | В терминале; оболочка остаётся открытой после завершения команды |
| `background` | `sh -c "<команда>"` без панели | Отбрасывается |
| `report` | `sh -c "<команда>"` без панели | Перехватывается и показывается в окне по завершении |

Фоновые команды и команды-отчёты появляются в панели [Операции](operations.md), которая открывается при их запуске. Запись исчезает, когда процесс завершается; отмена записи там убивает процесс вместе с дочерними. Других сигналов о завершении фоновая команда не даёт, поэтому, если её вывод нужен, перенаправьте его в файл. В Unix при установленном `direnv` фоновые команды и команды-отчёты также получают окружение, которое `direnv export json` возвращает для рабочего каталога.

### Окно отчёта

Когда команда-отчёт завершается, окно с заголовком из метки команды и `✓` (код выхода 0) или `✗` (любой другой код) показывает её вывод: сначала стандартный вывод, затем стандартный поток ошибок. Отступы и пустые строки внутри вывода сохраняются, табуляции разворачиваются в четыре пробела, пустые строки в начале и конце каждого потока отбрасываются; команда без вывода показывает `(no output)`. Окно открывается в текущем проекте, каким бы он ни был; для команды, запущенной в другом проекте, к заголовку добавляется путь этого проекта. Если несколько команд-отчётов завершились одновременно, показывается окно только последней.

| Клавиша | Действие |
|---------|----------|
| `↑` / `↓` (`k` / `j`) | Прокрутка на строку |
| `PageUp` / `PageDown` | Прокрутка на страницу |
| `Home` / `End` | В начало / в конец |
| Колесо мыши | Прокрутка |
| `Enter` / `Escape` | Закрыть окно |

## Параметры

Команда может объявить параметры. Перед запуском Termide показывает форму с заголовком `Параметры: <идентификатор>`, по полю на каждый параметр, и кнопками `Запуск` и `Отмена`. Каждое значение подставляется в строку команды на место своего [плейсхолдера](#плейсхолдеры) `{имя}` и, кроме того, передаётся в переменной окружения `TERMIDE_PARAM_<ИМЯ>`: имя в верхнем регистре, `-` заменён на `_`.

```toml
[deploy]
name = "Deploy"
command = "./deploy.sh {target} {dry-run}"
mode = "report"
key = "Ctrl+Shift+D"

[[deploy.params]]
name = "target"
label = "Target environment"
type = "select"
options = ["staging", "production"]
default = "staging"

[[deploy.params]]
name = "dry-run"
label = "Dry run"
type = "bool"
default = true
```

| Поле | Описание |
|------|----------|
| `name` | Обязательное; плейсхолдер — `{имя}`, переменная — `TERMIDE_PARAM_<ИМЯ>` |
| `label` | Подпись поля в форме; по умолчанию — `name` |
| `type` | `text` (по умолчанию), `number`, `bool` или `select` |
| `options` | Варианты для `select` |
| `default` | Начальное значение: строка, число или логическое значение |

| Тип | Поле | Передаваемое значение |
|-----|------|-----------------------|
| `text` | Текстовое поле | Текст как введён |
| `number` | Текстовое поле | Текст как введён; что это число, не проверяется |
| `bool` | Флажок, переключается `Space` / `Enter` или кликом | `true` или `false` |
| `select` | Выбор, переключается `←` / `→`; начинается с `default`, иначе с первого варианта | Выбранный вариант |

Форма показывается, как бы команда ни была запущена: из меню `Команды`, горячей клавишей или из командной палитры. Переменные доходят до команды в любом режиме; в режиме `terminal` они задаются в оболочке нового терминала и остаются в ней после завершения команды.

## Плейсхолдеры

`{имя}` в `command` (и в `build`) заменяется перед запуском: значением параметра `имя` или тем, что даёт панель в фокусе и проект. Параметр с тем же именем важнее.

| Плейсхолдер | Значение |
|-------------|----------|
| `{file}` | Файл редактора; в файловом менеджере — элемент под курсором |
| `{files}` | Выделенные в файловом менеджере файлы, каждый отдельным словом; без выделения — элемент под курсором; в редакторе — его файл |
| `{line}`, `{col}` | Позиция курсора в редакторе, с 1 |
| `{dir}` | Рабочая папка панели в фокусе |
| `{project}` | Корень проекта |

Пути абсолютные. Если файла нет — в фокусе, например, терминал или файл на удалённом сервере, — команда с `{file}`, `{files}`, `{line}` или `{col}` не запускается, и об этом выходит сообщение; выходит оно до формы параметров.

```toml
[p4-edit]
name = "p4 edit"
command = "p4 edit {file}"
key = "Alt+E"
```

Каждое значение экранируется для того, кто читает строку, поэтому путь с пробелами, кавычками или `;` остаётся одним аргументом и никогда не выполняется как команда:

- команды `background` и `report` запускаются через `sh -c`: POSIX-кавычки;
- команды `terminal` экранируются для оболочки терминала: POSIX для sh, bash, zsh и подобных, собственные правила fish для fish, `'…'` для PowerShell, `"…"` для cmd. В cmd нет буквального экранирования, так что `%имя%` в значении там всё равно раскрывается;
- строка отладочной команды сначала делится на слова, и значения подставляются в них, каждое одним словом (`{files}` — несколькими); её `build` получает POSIX-кавычки.

Плейсхолдер может стоять где угодно: отдельным словом (`p4 edit {file}`), в кавычках (`"{file}"`) или внутри более длинной строки в кавычках (`"at {file}"`, `'at {file}'`). Значение экранируется под это место и в любом случае берётся буквально: файл с именем `$(rm -rf ~).c` — всего лишь имя. `{files}` в кавычках даёт одно слово, как и всё в кавычках. Плейсхолдер, экранированный для оболочки (`\{file}` в sh, `` `{file} `` в PowerShell, `^{file}` в cmd), остаётся как написан. Заменяются только перечисленные имена и параметры команды: остальные фигурные скобки остаются как есть, так что `awk '{print $1}'`, `docker inspect -f '{{.Name}}'`, раскрытие скобок и `${VAR}` не затрагиваются.

## Горячие клавиши

`key` записывается в той же нотации, что и сочетания в `config.toml` (см. [keybindings.md](keybindings.md)), например `Ctrl+Shift+D` или `Alt+F6`. `Ctrl+Shift+<буква>` доходит до Termide только в терминалах с протоколом клавиатуры Kitty (см. [Универсальные vs расширенные биндинги](keybindings.md#универсальные-vs-расширенные-биндинги)). Горячая клавиша команды проверяется вместе с глобальными сочетаниями Termide, поэтому работает независимо от того, какая панель в фокусе. Команда проекта и глобальная команда с одинаковым идентификатором сохраняют отдельные горячие клавиши.

Команды с горячей клавишей также перечислены в командной палитре (`Ctrl+P`) как `Run command: <название>`.

Поле `Хоткей:` в форме принимает `Ctrl`, `Alt` и `Shift` в сочетании с буквой, цифрой, `F1`–`F12` или именованной клавишей (`Enter`, `Tab`, `Space`, `Home`, `PageUp`, стрелки и т. д.) и отклоняет горячую клавишу, которую уже использует другая команда или глобальное сочетание Termide (`Этот хоткей уже используется`). Горячая клавиша, записанная в файл вручную, не проверяется: если она совпадает с глобальным сочетанием, срабатывает сочетание, и команда с клавиатуры не запускается никогда. Она начинает действовать при следующем открытии меню `Команды` или после сохранения файла из Termide.

## Отладка

Команда с `debugger` отлаживает программу с точками останова, расставленными в редакторе (см. [Точки останова](editor.md#точки-останова-и-отладка)), и выполняет её до первой из них. `command` в этом случае — то, что отлаживается. Поддерживаются два вида отладчиков:

- **отладочный адаптер**, которым Termide управляет по Debug Adapter Protocol и показывает в [панели отладки](#панель-отладки): `lldb-dap`, `gdb-dap`, `debugpy`, `dlv-dap`;
- **консольный отладчик** в новой панели терминала, где шаги, вывод значений и продолжение делаются его собственными командами: `lldb`, `gdb`, `dlv`, `pdb`.

| `debugger` | `command` — это | Запускается как |
|------------|-----------------|-----------------|
| `lldb-dap` | программа и её аргументы | `lldb-dap` из LLVM (в macOS ищется и через `xcrun`; в старых LLVM — `lldb-vscode`): Rust, C, C++ |
| `gdb-dap` | программа и её аргументы | `gdb -i dap`, GDB 14 и новее |
| `debugpy` | скрипт и его аргументы | `python3 -m debugpy.adapter`; нужен `pip install debugpy` |
| `dlv-dap` | собираемый пакет и аргументы, например `./cmd/app --flag` | `dlv dap`, адаптер Delve, связь через локальный TCP-порт; где `/proc/net/tcp` не читается (Termux на Android) — с `--only-same-user=false`, иначе проверка пользователя в Delve отвергает любое подключение |
| `lldb` | программа и её аргументы | `lldb -s <сценарий> -- <command>` |
| `gdb` | программа и её аргументы | `gdb -q -x <сценарий> --args <command>` |
| `dlv` | подкоманда Delve и её аргументы, например `debug ./cmd/app` | `dlv --init <сценарий> <command>` |
| `pdb` | скрипт и его аргументы | `python3 -m pdb -c 'break <файл>:<строка>' … -c continue <command>` |

```toml
[debug-app]
name = "Отладка app"
command = "target/debug/app --verbose"
debugger = "lldb-dap"
build = "cargo build"
key = "Ctrl+Alt+D"
```

`debugger_args` задаёт собственные флаги отладчика — массивом слов, которые добавляются к тем, с которыми его запускает Termide:

```toml
[debug-go]
command = "./cmd/app"
debugger = "dlv-dap"
debugger_args = ["--log", "--log-output=dap"]
```

Они встают туда, где отладчик читает свои параметры, — до программы: адаптер получает их после своих аргументов (`dlv dap --listen=… --log …`, `gdb -i dap …`), `lldb` и `gdb` — до `--` и `--args`, `dlv` — до подкоманды, `pdb` — до своих `-c`. Аргументы программы остаются в `command`.

Для отладочного адаптера `command` делится на слова так, как это сделала бы оболочка (кавычки и обратная косая черта работают), но оболочка его не запускает: переменные, `~` и шаблоны не раскрываются. Сначала выполняется `build`, его вывод идёт в панель отладки; адаптер запускается, только если сборка прошла успешно. Консольный отладчик получает точки останова из сценария — на каждую `breakpoint set` или `break`, в конце `run` (lldb, gdb) или `continue` (Delve), — который записывается в `termide-debug` во временном каталоге системы; точки, поставленные во время его работы, попадут в него только при следующем запуске, а пока ставьте их в самом отладчике.

Передаются только точки останова в файлах внутри корня проекта, и каждая — отладчику своего языка: файлы Python — debugpy и pdb, файлы Go — Delve и dlv-dap, остальные — lldb и gdb. Отладочные команды запускаются в корне проекта, поэтому относительный путь к программе вроде `target/debug/app` означает одно и то же, где бы ни был фокус. Параметры работают так же, как у других команд; отладочному адаптеру и сборке они передаются переменными окружения.

`F5` в редакторе (`start_debug`) или **Начать отладку** в палитре команд начинает отладку: если запуск один, он начинается сразу, если их несколько — они предлагаются списком. Запуски — это отладочные команды проекта и глобального файла, а если в редакторе в фокусе файл Python, Go или Rust — ещё и сам этот файл, для которого команда не нужна:

- скрипт Python запускается под debugpy в панели отладки, если debugpy установлен, а иначе под pdb в терминале;
- пакет из каталога файла Go — под `dlv dap` в панели отладки, если Delve установлен, а иначе под `dlv debug` в терминале;
- файл Rust в проекте Cargo предлагает бинарники, найденные через `cargo metadata`: тот, чей это главный файл, иначе бинарники его пакета, иначе все бинарники рабочего пространства. Каждый собирается командой `cargo build -p <пакет> --bin <имя>` и запускается из корня рабочего пространства под `lldb-dap`, адаптером GDB или `lldb` в терминале — первым из установленных.

Если файл можно отладить, но отладчика нет (LLDB или GDB для Rust, Delve для Go), окно сообщает, что установить. Если запускать нечего совсем, вместо этого открывается форма **Настройка отладки** (см. ниже). Пока сеанс отладки активен, `F5` вместо этого продолжает выполнение.

**Настроить отладку…** в меню `[≡]` редактора и в палитре команд открывает форму своего запуска: название, программа и её аргументы, команда сборки перед запуском, отладчик и его флаги (делятся на слова, как в оболочке) — заполненные для файла в редакторе, для бинарника Rust это путь в `target/debug` и его `cargo build`. **Запуск** сохраняет его отладочной командой в `.termide/commands.toml` проекта и начинает отладку; дальше `F5` предлагает эту команду, а изменить её — например, добавить аргументы — можно там же или в меню команд.

### Настройки отладчиков

Как запускается каждый отладчик, задаётся в `config.toml`, отдельно от того, что отлаживается. `.termide/config.toml` проекта может задать `native` и `console`; `command` и `args` отладчиков берутся только из глобального файла, потому что они называют программу, которую запускает termide:

```toml
[debug]
native = ["lldb-dap", "gdb-dap", "lldb"]  # Rust, C, C++ без команды: первый установленный
console = "terminal"                      # или "panel": где адаптер по умолчанию запускает программу

[debug.debuggers.lldb-dap]
command = "/opt/homebrew/opt/llvm/bin/lldb-dap"  # вместо найденного в PATH (или через xcrun)

[debug.debuggers.dlv-dap]
args = ["--log"]                                 # флаги для каждого запуска
```

- `command` — программа отладчика: путь (`~/` означает домашний каталог) или имя, которое ищется в `PATH`. Для `debugpy` и `pdb` это Python, которым их запускать. Если указанного пути нет, отладчик считается неустановленным, а не заменяется другим.
- `args` — флаги отладчика для каждого запуска вместо его флагов по умолчанию; `debugger_args` запуска идут после них. Без `args` остаются флаги по умолчанию, `[]` их убирает. Сейчас такой флаг один: `--only-same-user=false` для `dlv-dap` там, где `/proc/net/tcp` не читается (Termux на Android), иначе проверка пользователя в Delve отвергает любое подключение. Если в такой системе задать `args` для `dlv-dap`, он заменится, поэтому при необходимости укажите его снова.
- Аргументы, без которых Termide не может говорить с адаптером (`dap --listen=…` у Delve, `-i dap` у GDB, `-m debugpy.adapter`), и сценарии консольных отладчиков передаются всегда и не меняются.
- `native` перебирается по порядку для файла Rust, который отлаживается без команды; в нём допустимы `lldb-dap`, `gdb-dap`, `lldb` и `gdb`.
- `console` действует на запуски, где свой `console` не указан.

Вкладка **Отладка** в окне настроек правит то же самое: порядок и консоль, затем все известные Termide отладчики с их программой и флагами, а значения по умолчанию помечены. Отладчик открывается на своей странице; флаги вводятся так, как их разделила бы оболочка (кавычки сохраняют значение целым, запятая — часть флага), пустое поле означает «без флагов», а **Сбросить** возвращает программу из `PATH` и флаги по умолчанию, а в настройках проекта — глобальные.

### Панель отладки

Запуск через отладочный адаптер открывает панель отладки (или использует уже открытую). В её верхней строке — сеанс и его состояние: сборка, запуск, выполнение, остановка и её причина, завершение с кодом или ошибка с причиной, — и клавиши. Ниже три раздела:

- **Стек вызовов** — кадры остановившегося потока, начиная с самого вложенного, у каждого файл и строка. `Enter` или клик по кадру показывает его переменные и его строку в редакторе.
- **Переменные** — области видимости выбранного кадра; первая из тех, что дёшево получить, раскрывается сама. `Enter`, `Пробел` или `→` раскрывает переменную с полями (при первом раскрытии они запрашиваются у адаптера), `←` сворачивает её или переходит к родителю; повторный клик по строке тоже раскрывает и сворачивает.
- **Вывод** — стандартный вывод и ошибки программы, сообщения адаптера, вывод сборки и вычисленные выражения с их значениями. Раздел следит за новым выводом; `↑`/`PgUp` прокручивают назад, `Enter` возвращает к концу.

| Клавиша | Действие |
|---------|----------|
| `c` / `F5` | Продолжить |
| `n` | Шаг с обходом |
| `s` | Шаг с заходом |
| `o` | Шаг с выходом |
| `p` | Приостановить работающую программу |
| `x` | Стоп: завершить сеанс и программу |
| `r` | Перезапуск: выполнить тот же запуск заново — сначала его `build`, с теми же параметрами, — завершив сеанс, если он ещё идёт |
| `e` | Вычислить выражение в выбранном кадре |
| `Tab` / `Shift+Tab` | Следующий / предыдущий раздел |
| `↑` `↓` `PgUp` `PgDn` `Home` `End` | Перемещение в разделе |

Когда программа останавливается, редактор с этим файлом переводит курсор на строку, прокручивая ровно настолько, насколько нужно, и отмечает её на поле номеров знаком `→` на подсвеченной клетке; ещё не открытый файл открывается в новом редакторе, а фокус остаётся на панели. Точки останова, поставленные или снятые во время сеанса, сразу передаются адаптеру. Закрытие панели или новый запуск завершают сеанс и программу.

### Терминал программы

По умолчанию (`console = "terminal"`) программа работает в собственной панели терминала, открытой рядом с остальными: там она читает клавиатуру — переведите фокус на эту панель, чтобы вводить, — а её вывод, цвета и полноэкранные интерфейсы видны там, как в любом терминале; в панели отладки остаются сообщения адаптера. debugpy и Delve просят Termide запустить программу в этой панели; lldb-dap запускает её сам, а устройство терминала панели получает через настройки lldb `target.input-path`, `output-path` и `error-path`, которые понимает любая версия lldb-dap. `Ctrl+C` в терминале, который использует lldb-dap, программе не передаётся: приостановите её клавишей `p` в панели отладки. У адаптера GDB такого режима нет, поэтому его программы всегда пишут в панель отладки и ничего не читают; так же работают сеансы, запущенные агентом, — он читает вывод из сеанса. `console = "panel"` включает это для любого адаптера, если программе не нужен ввод.

## Советы

- Команды выполняются через `sh -c` (или оболочку терминала), поэтому конвейеры, `&&`, перенаправления и переменные окружения работают как в оболочке. В Windows для команд `background` и `report` нужен `sh` в `PATH`.
- Используйте `report` для коротких проверок, результат которых хочется прочитать (`git status`, линтер), `background` — для процессов, вывод которых не нужен, и `terminal` — для всего интерактивного или долгого, за чем хочется следить.
- Держите команды, относящиеся к проекту, в `.termide/commands.toml` в репозитории, а личные — в глобальном файле.
