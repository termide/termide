# Руководство разработчика

Это руководство для разработчиков, которые хотят внести вклад в Termide или понять его кодовую базу.

## Настройка окружения разработки

### Требования

- **Rust** — версия зафиксирована в `rust-toolchain.toml`; rustup сам
  установит и выберет её при первой команде `cargo` в каталоге проекта
- **Git** для контроля версий
- **Компилятор C** для грамматик tree-sitter, которые собирает `build.rs`:
  gcc или clang на Linux, Xcode Command Line Tools
  (`xcode-select --install`) на macOS, MSVC на Windows
- **Опционально:** Nix с включёнными flakes для воспроизводимых сборок

Больше ничего не нужно. Проект целиком написан на Rust: FTPS использует
rustls с webpki-roots, SFTP — russh, поэтому ни OpenSSL, ни libssh2
устанавливать не требуется. Это же делает возможной полностью статическую
сборку под musl.

### Получение исходного кода

```bash
git clone https://github.com/termide/termide.git
cd termide

# Активировать git-хуки из репозитория (один раз на клон)
git config core.hooksPath .githooks
```

### Сборка

#### С помощью Cargo (стандартно)

```bash
# Сборка для разработки
cargo build

# Release-сборка с оптимизациями
cargo build --release

# Запуск в режиме разработки
cargo run

# Запуск в release-режиме
cargo run --release
```

#### С помощью Nix (воспроизводимо)

```bash
# Войти в окружение разработки со всеми зависимостями
nix develop

# Собрать с помощью Nix
nix build

# Запустить проверки
nix flake check
```

Окружение разработки и `nix build` берут версию компилятора из
`rust-toolchain.toml` — того же файла, который используют rustup и CI, — поэтому
сборка под Nix и без него идёт одним и тем же компилятором.

#### Особенности платформ

CI прогоняет fmt / clippy / test на Linux и macOS; Windows и
кросс-компилируемые цели собираются на этапе релиза. Код, обращающийся к
средствам операционной системы, требует отдельной ветки под каждую платформу —
так уже сделано для получения сведений о процессах (`/proc` на Linux, libproc
на macOS, снимки ToolHelp на Windows), таблицы монтирования (`/proc/mounts`
против `getmntinfo`) и флагов расширенной клавиатуры.

В Linux сборка компонуется компоновщиком по умолчанию из тулчейна: rust-lld на
x86_64, системным `ld` на остальных архитектурах. Компоновка бинарника занимает
около секунды с lld и вдвое меньше с [mold](https://github.com/rui314/mold),
против шести с GNU `ld`; чтобы ваши сборки шли через mold (или `lld`),
установите его и добавьте в `~/.cargo/config.toml`:

```toml
[target.aarch64-unknown-linux-gnu]   # или x86_64-unknown-linux-gnu
rustflags = ["-C", "link-arg=-fuse-ld=mold"]
```

### Запуск тестов

```bash
# Запустить все тесты (корневой крейт — тоже пакет: без --workspace
# запускаются только его тесты)
cargo test --workspace

# Запустить тесты с выводом
cargo test --workspace -- --nocapture

# Запустить конкретный тест
cargo test --workspace test_name

# Быстрее, как в pre-commit хуке и CI (cargo install cargo-nextest)
cargo nextest run --workspace
```

Поведение интерфейса и агента проверяется вживую через
[`tools/tui-harness`](../../tools/tui-harness/README.md): он запускает
собранный бинарник без окна, в pty, по сценариям (клавиши, ожидания,
проверки экрана), с одноразовым HOME, демо-проектом и мок-моделью или
мок-агентами ACP.

```bash
cargo build
tools/tui-harness/run.sh           # все сценарии
tools/tui-harness/run.sh agent     # один из них
```

### Проверка качества кода

```bash
# Запустить линтер clippy (включает проверки компилятора; отдельный cargo check не нужен)
cargo clippy --workspace --all-targets -- -D warnings

# Форматировать код
cargo fmt --all

# Проверить форматирование без изменения файлов
cargo fmt --all -- --check

# Найти неиспользуемые зависимости (cargo install cargo-machete)
cargo machete
```

Это проверки pre-commit хука (`.githooks/pre-commit`, включается командой
`git config core.hooksPath .githooks`): проверки заголовков документации и
версии, fmt, machete, clippy и тесты. CI вдобавок запускает `cargo deny check`
и doctest'ы (`cargo test --workspace --doc`, их nextest пропускает); в хуке их
нет.

## Ключевые компоненты

### 1. LayoutManager (`crates/layout/src/`)

Владеет состоянием split-компоновки всего окна:
- Горизонтальное расположение `Vec<PanelGroup>` (каждая группа — колонка)
- Навигация фокуса между группами (Alt+Left/Right)
- Умное стекирование/разделение панелей между соседними группами (Alt+Backspace, F11)
- Пропорциональное перераспределение ширин при ресайзе терминала
- Адаптивный дефолтный layout через `setup_default_layout()`

### 2. PanelGroup (`crates/layout/src/panel_group.rs`)

Колонка вертикально расположенных панелей с регулируемыми высотами:
- `expanded_index: usize` — фокусная панель (активная рамка + панель, увеличенная fullscreen-пресетом, когда он активен)
- `width: Option<u16>` — ширина колонки (None = авто-распределение)
- `split_heights: Option<Vec<u16>>` — кеш per-panel высот, пропорционально пересчитывается при ресайзе
- `fullscreen_cache: Option<Vec<u16>>` — высоты для restore при выключении fullscreen-пресета (`Alt+F11`)
- `next_panel`/`prev_panel`/`set_expanded` перемещают фокус и переприменяют пресет, если он активен
- `grow_focused`/`shrink_focused` увеличивают/уменьшают фокусную панель (шаг 1 строка), каскадно через соседей
- `resize_panel_divider` применяет дельту к разделителю над указанной панелью (используется обработчиком mouse drag)

### 3. Трейт Panel (`crates/core/src/lib.rs`)

Все панели реализуют этот трейт:
```rust
pub trait Panel {
    fn render(&mut self, area: Rect, buf: &mut Buffer, is_focused: bool, panel_index: usize, state: &AppState);
    fn handle_key(&mut self, key: KeyEvent) -> Result<()>;
    fn handle_mouse(&mut self, mouse: MouseEvent, panel_area: Rect) -> Result<()>;
    fn title(&self) -> String;
    fn is_welcome_panel(&self) -> bool { false }
    // ... другие методы
}
```

### 4. Обработка событий (`crates/app/src/app/`)

**Поток:**
1. `EventHandler` опрашивает события терминала
2. События направляются в соответствующий обработчик:
   - `key_handler.rs` для клавиатуры
   - `mouse_handler.rs` для мыши
   - `modal_handler.rs` для модальных окон
3. Обработчики обновляют `LayoutManager` и состояния панелей
4. UI перерисовывается на следующем кадре

### 5. Управление состоянием (`crates/state/src/`)

Разделено на модули: `batch.rs`, `layout.rs`, `operations.rs`, `pending_action.rs`, `ui.rs`.

`AppState` содержит:
- Конфигурацию темы
- Размеры терминала
- Наблюдатель файловой системы
- Состояние пакетных операций
- Состояние модальных окон
- UI-состояние (меню, подменю, перетаскивание)

### 6. Интернационализация (`crates/i18n/`)

Поддерживается 15 локалей (en, ru, de, es, fr, pt, ja, ko, zh, bn, hi, id, th, tr, vi); словари — TOML-файлы в `crates/i18n/i18n/*.toml`. Trait `Translation` и его реализация `RuntimeTranslation` предоставляют типобезопасный доступ к строкам.

**Fallback на английский.** Если ключ отсутствует в текущей локали, `RuntimeTranslation` автоматически отдаёт английское значение и пишет warning в лог:

```
WARN Missing translation key: my_key (using English fallback)
```

Это защищает UI от пустых строк при неполных переводах. Для не-английских локалей англ. словарь всегда загружается вторым вместе с основным.

**Как добавить ключ:**
1. Добавить метод в trait `Translation` (`crates/i18n/src/lib.rs`).
2. Добавить реализацию в `RuntimeTranslation` (`crates/i18n/src/runtime.rs`) — обычно `self.get_string("ключ")` или `self.format("ключ", &[...])` для форматов с placeholder'ами.
3. Добавить запись во все 15 `*.toml`-файлов (отсутствующие подхватятся fallback'ом, но предпочтительно перевести сразу).

**Как удалить ключ:** убрать метод из trait, реализацию из runtime, и строки из всех 15 словарей. Синхронизация проверяется сравнением ключей `en.toml` с остальными локалями.

## Соглашения по коду

### Стиль

- Следуйте стандартному стилю Rust (применяется `cargo fmt`)
- Используйте осмысленные имена переменных
- Держите функции сфокусированными и небольшими
- Добавляйте комментарии для сложной логики

### Обработка ошибок

- Используйте `anyhow::Result` для распространения ошибок
- Используйте `.context()` или `.with_context()` для добавления контекста ошибок
- Избегайте `.unwrap()` - используйте `.expect()` с описательным сообщением или правильную обработку ошибок
- Логируйте ошибки в `state.log_error()` для отладки

### UI код

- Используйте виджеты `ratatui` для рендеринга
- Держите логику рендеринга отдельно от бизнес-логики
- Тщательно рассчитывайте размеры (учитывайте границы, отступы)
- Тестируйте UI при разных размерах терминала

### Реализация панели

При создании новой панели:

1. Реализуйте трейт `Panel`
2. Обработайте ввод с клавиатуры в `handle_key()`
3. Обработайте ввод мыши в `handle_mouse()`
4. Реализуйте правильный рендеринг в `render()`
5. Верните осмысленный `title()` для заголовка панели
6. Добавьте создание панели в `app/mod.rs` или меню

## Тестирование

### Чек-лист ручного тестирования

При внесении изменений проверьте:
- [ ] Разные размеры терминала (изменение размера во время работы)
- [ ] Навигацию с клавиатуры (все горячие клавиши)
- [ ] Взаимодействия с мышью (клики, прокрутка)
- [ ] Модальные диалоги (открытие, закрытие, взаимодействие)
- [ ] Управление панелями (открытие, закрытие, стекирование, разделение)
- [ ] Переключение тем
- [ ] Как английский, так и русский UI

### Частые проблемы

**Глюки рендеринга панелей:**
- Проверьте вычисления границ
- Убедитесь, что area.width/height учитывают границы (вычесть 2)
- Тестируйте при минимальной ширине (80 символов)

**Проблемы с фокусом:**
- Проверьте, что FocusTarget обновляется корректно
- Проверьте обработку фокуса в обработчиках событий
- Тестируйте навигацию с пустыми группами

**Утечки памяти:**
- Убедитесь, что панели правильно удаляются при закрытии
- Проверьте циклические ссылки
- Мониторьте с помощью `cargo clippy`

## Рабочий процесс вклада

1. **Сделайте форк** репозитория
2. **Создайте ветку** для вашей функции/исправления
3. **Внесите изменения**, следуя соглашениям по коду
4. **Тщательно протестируйте** (см. чек-лист выше)
5. **Запустите проверки качества кода:**
   ```bash
   cargo fmt --all
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   ```
6. **Сделайте коммит** с чёткими, описательными сообщениями
7. **Отправьте** в ваш форк
8. **Откройте Pull Request** с:
   - Чётким описанием изменений
   - Почему изменение необходимо
   - Результатами тестирования
   - Скриншотами для изменений UI

## Отладка

### Логирование

Каждый запуск пишет свой лог в `logs/YYYYMMDD-HHMMSS-mmm.log` в каталоге
данных проекта (`~/.local/share/termide/projects/<имя>-<хеш>/` в Linux,
`~/Library/Application Support/termide/projects/<имя>-<хеш>/` в macOS); логи
старше 24 часов удаляются при запуске, а журнал больше 10 МБ откладывается
как `<имя>.1` и начинается заново. Файл доступен на чтение только вам. Раздел `[logging]` меняет это:

```toml
[logging]
file_path = "/tmp/termide.log"  # вместо этого один постоянный файл; только в глобальном конфиге
min_level = "info"              # trace, debug, info, warn или error (по умолчанию: info)
```

`--log-level` заменяет `min_level` на один запуск, не сохраняя его. Те же
записи видны в панели журнала (`Alt+L`).

Используйте логирование в коде:
```rust
state.log_info("Информационное сообщение");
```

### Панель логов

Откройте с помощью `Alt+L`:
- Показывает состояние приложения
- Отображает последние записи логов
- Показывает информацию о панелях
- Полезно для разработки

### Частые задачи отладки

**Панель не рендерится:**
1. Проверьте, что панель находится в группе: `layout_manager.panel_groups`
2. Убедитесь, что фокус правильный: `layout_manager.focus`
3. Проверьте, что область рендеринга не нулевая

**Ввод с клавиатуры не работает:**
1. Проверьте, не открыто ли модальное окно (захватывает ввод)
2. Убедитесь, что панель имеет фокус
3. Проверьте трансляцию клавиш (поддержка кириллицы)

**Использование памяти растёт:**
1. Запустите с `valgrind` или аналогом
2. Проверьте неограниченные коллекции
3. Убедитесь, что панели удаляются при закрытии

## Соображения производительности

### Рендеринг

- Минимизируйте дорогие операции в `render()`
- Кешируйте вычисленные значения, когда возможно
- Используйте размеры `area` для ограничения работы
- Профилируйте с помощью `cargo flamegraph` при необходимости

- Используйте асинхронные операции, где уместно
- Реализуйте дебаунсинг для событий файловой системы
- Ограничивайте глубину обхода директорий

- Группируйте записи в терминал
- Минимизируйте перерисовки экрана
- Используйте частичные обновления, когда возможно
